# 连接树结构优化 - 产品需求文档

## Overview
- **Summary**: 优化数据库连接树的结构，为不同数据库类型提供准确的元数据层次结构展示
- **Purpose**: 解决当前连接树结构不准确的问题，使每个数据库类型都按照其标准的元数据层次展示（数据库→模式/表→对象类型→具体对象）
- **Target Users**: 使用 LinkBase 桌面应用进行数据库管理的用户

## Goals
1. 为 MySQL 提供正确的树结构：连接 → 数据库 → [表、视图、存储过程、函数、触发器、事件、用户]
2. 为 PostgreSQL 提供正确的树结构：连接 → 数据库 → 模式 → [表、视图、物化视图、存储过程、函数、触发器、事件、序列、索引、角色、表空间]
3. 支持新的数据库对象类型：触发器、事件、角色、表空间
4. 更新现有驱动以支持新元数据类型的查询

## Non-Goals (Out of Scope)
- 不重构其他数据库驱动（SQLite、Oracle）的元数据查询，除非必要
- 不更改现有的 API 调用方式，保持向后兼容性
- 不添加元数据编辑功能，仅展示

## Background & Context
LinkBase 当前实现了基础的连接树展示，但树结构与各数据库的标准元数据层次不完全匹配：
- MySQL 缺少触发器、事件的分类
- PostgreSQL 缺少数据库层、角色、表空间，且当前仅展示模式层
- 需要扩展元数据类型定义，支持新增的对象类型

## Functional Requirements
- **FR-1**: 扩展数据库元数据类型定义，添加触发器、事件、角色、表空间等类型
- **FR-2**: 更新 MySQL 驱动，支持查询触发器和事件
- **FR-3**: 更新 PostgreSQL 驱动，支持查询数据库、角色、表空间等
- **FR-4**: 更新 TREE_NODE_TEMPLATES，定义各数据库类型的正确树结构
- **FR-5**: 更新 ConnectionTree 组件，支持新树结构的渲染

## Non-Functional Requirements
- **NFR-1**: 保持查询性能，新增的元数据查询不应显著降低连接速度
- **NFR-2**: 保持代码风格一致性，遵循项目现有规范
- **NFR-3**: 保持向后兼容，不破坏现有功能

## Constraints
- **Technical**: 必须在现有的 Rust+Vue+Tauri 架构内实现
- **Business**: 优先完成 MySQL 和 PostgreSQL 的支持
- **Dependencies**: 依赖 sqlx 库进行数据库查询

## Assumptions
- 用户已安装并配置好相应数据库
- 用户有足够的权限查询系统元数据表
- 现有的树渲染逻辑可以扩展支持新结构

## Acceptance Criteria

### AC-1: 数据类型扩展
- **Given**: 项目已打开
- **When**: 查看 db-common 库的类型定义
- **Then**: 应包含 TriggerInfo、EventInfo、RoleInfo、TablespaceInfo 等新类型
- **Verification**: programmatic
- **Notes**: 验证类型定义是否正确添加

### AC-2: MySQL 树结构正确
- **Given**: 成功连接 MySQL 数据库
- **When**: 展开连接树
- **Then**: 树结构应为：连接 → 数据库 → [表、视图、存储过程、函数、触发器、事件] + 用户
- **Verification**: human-judgment
- **Notes**: 验证树节点层次和分类是否正确

### AC-3: PostgreSQL 树结构正确
- **Given**: 成功连接 PostgreSQL 数据库
- **When**: 展开连接树
- **Then**: 树结构应为：连接 → 数据库 → 模式 → [表、视图、物化视图、存储过程、函数、触发器、事件、序列、索引] + 角色、表空间
- **Verification**: human-judgment
- **Notes**: 验证树节点层次和分类是否正确

### AC-4: 新对象类型能正确显示
- **Given**: 数据库中存在触发器、事件等对象
- **When**: 在连接树中查看相应分类
- **Then**: 应能看到对象列表并正确显示
- **Verification**: human-judgment
- **Notes**: 验证新对象类型的展示
